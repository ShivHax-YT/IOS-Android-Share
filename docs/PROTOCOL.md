# NearPair wire protocol v1

## Transport identity

- Nearby Connections service ID: `com.nearpair.transfer.v1`
- Strategy: point-to-point
- Participants: exactly one sender and one receiver
- Apps: foreground on both endpoints for the entire direct-transfer session
- Transport security: Nearby Connections encrypted channel after both users approve the matching authentication digits

On iOS the service ID maps to Bonjour service `_EBD1B4122871._tcp`. This is the uppercase first 12 hexadecimal characters of the SHA-256 digest of the UTF-8 service ID, wrapped as `_<digest>._tcp`, matching Google's Nearby Swift setup and sample format.

## File policy

Protocol v1 accepts only:

- `application/pdf`
- MIME types beginning with `image/`
- MIME types beginning with `video/`

`fileName` is display metadata, not a path. A receiver must strip directory components, control characters, leading dots, and platform path separators. A receiver may add a suffix to prevent overwriting an existing inbox item. Files are never auto-opened.

## Payload identifiers

Every transfer has two identifiers:

- `transferId`: a UUID string generated by the sender for application-level correlation.
- `payloadId`: the signed 64-bit Nearby file/resource payload identifier. The sender explicitly assigns this identifier on both platforms and includes it in metadata.

Bytes payloads have their own Nearby payload identifiers and are not correlated by arrival order. Nearby does not guarantee ordering between bytes and file/resource payload types, so a receiver must tolerate metadata or the file arriving first.

## Messages

Messages are UTF-8 JSON sent as Nearby bytes payloads. Unknown fields must be ignored. Unknown `type` values or unsupported `version` values terminate the transfer with an `error` message when possible.

### Metadata

```json
{
  "type": "metadata",
  "version": 1,
  "transferId": "7e51382d-1d59-4b7a-b327-c2d0a87d2eb9",
  "payloadId": 123456,
  "fileName": "vacation-video.mp4",
  "mimeType": "video/mp4",
  "sizeBytes": 2147483648,
  "sha256": "4f64b8c2b7b7423a88994bd53017c9c8f6f8f739d31513798b7f18df0e07f1d2"
}
```

Validation:

- `version` is exactly `1`.
- `transferId` parses as a UUID.
- `payloadId` is a signed 64-bit integer. Nearby generates this value, so implementations must accept the full signed range, including negative values.
- `fileName` is non-empty after sanitization and at most 255 UTF-8 bytes after receiver normalization.
- `mimeType` is in the v1 allowlist.
- `sizeBytes` is greater than zero.
- `sha256` is exactly 64 lowercase hexadecimal characters.

### Verified acknowledgement

```json
{
  "type": "verified",
  "version": 1,
  "transferId": "7e51382d-1d59-4b7a-b327-c2d0a87d2eb9",
  "payloadId": 123456
}
```

The receiver sends this only after the Nearby resource succeeds, the staged inbox copy has exactly `sizeBytes`, and its SHA-256 equals `sha256`. The sender displays **Delivered** only after receiving and validating this acknowledgement.

### Error acknowledgement

```json
{
  "type": "error",
  "version": 1,
  "transferId": "7e51382d-1d59-4b7a-b327-c2d0a87d2eb9",
  "payloadId": 123456,
  "code": "insufficientStorage"
}
```

Allowed v1 codes are `unsupportedVersion`, `invalidMetadata`, `unsupportedType`, `insufficientStorage`, `sizeMismatch`, `checksumMismatch`, `rejected`, `cancelled`, and `ioFailure`. Human-readable recovery text is local UI copy and is never trusted from the remote endpoint.

## Sequence

1. Receiver advertises its locally chosen display name.
2. Sender discovers and explicitly selects one receiver.
3. Sender requests a Nearby connection.
4. Both apps display the authentication digits. Neither app verifies/accepts the secure connection without an explicit user action.
5. Once connected, sender assigns the file/resource `payloadId`.
6. Sender sends metadata bytes, then the file/resource payload. Receiver supports either arrival order.
7. On metadata arrival, receiver validates fields and available storage. Required free capacity is `sizeBytes` plus a 5%/32 MiB safety margin, whichever is greater.
8. Receiver tracks Nearby progress using `payloadId`. A receive callback is not completion.
9. After Nearby reports success, receiver copies/moves the resource to its private inbox, verifies byte size and SHA-256, and removes the Nearby temporary resource where the platform allows.
10. Receiver sends `verified`.
11. Receiver offers Save, Share, or Delete. Sender shows Delivered only after step 10.

## Terminal failures

Rejection, cancellation, connection loss, unsupported protocol, storage failure, I/O failure, size mismatch, or checksum mismatch terminates the v1 session. Both endpoints stop advertising/discovery, cancel the active payload when possible, disconnect, and offer a new transfer retry. V1 does not resume partial files.

## Compatibility

Protocol implementations reject any `version` other than `1`. Future compatible additive fields may remain on version 1 only when v1 receivers can ignore them safely. Any semantic change to sequencing, identifiers, integrity rules, service ID, authentication requirements, or accepted file classes requires a new protocol version and a coordinated Android/iOS release.
